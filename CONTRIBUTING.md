# Contributing to GAAex

A practical guide to running, testing, and extending GAAex. For the full architecture vision,
read `../GAAex-Vision/` (start at its `README.md`); this file is about the build in this repo.

---

## 1. Run it (dev)

**Prerequisites:** Docker, Python 3.11+, Node 18+.

```bash
# 1. start the infrastructure — Postgres on :5433, Redis on :6380
docker compose up -d

# 2. backend (first time: create the venv + install deps)
cd backend
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt    # Windows
.venv/Scripts/python.exe -m alembic upgrade head               # apply migrations (see §2)
.venv/Scripts/python.exe -m uvicorn app.main:app --port 8099
```

```bash
# 3. frontend (separate terminal)
cd frontend
npm install
npm run dev        # http://localhost:5173 (auto-bumps to 5174… if the port is taken)
```

**Ports & URLs**

| What | Where |
|------|-------|
| API (Swagger) | http://127.0.0.1:8099/docs |
| Health | http://127.0.0.1:8099/health · `/health/db` |
| Org tree | http://127.0.0.1:8099/org-tree |
| Frontend | http://localhost:5173 |
| Postgres | `localhost:5433` (user / pass / db = `gaaex`) |
| Redis | `localhost:6380` |

**Demo logins** (seeded automatically on first boot):

| User | Email | Password | Role / scope |
|------|-------|----------|--------------|
| Admin | `admin@demo.isp` | `admin123` | `super_admin`, tenant-wide |
| Agent | `agent@demo.isp` | `agent123` | `sales_agent`, single team node |

Use these to see access control in action — the agent sees only its own org subtree and a
narrower set of permissions than the admin.

> Config is environment-driven (`backend/app/config.py`, loaded from `backend/.env`). The
> defaults point at the Docker services above, so a plain `docker compose up -d` needs no `.env`
> for local dev. **Set a real `JWT_SECRET` (32+ bytes) before any non-local use.**

## 2. Database & migrations

Schema is managed by **Alembic** (`backend/alembic/`); the app does **not** create tables on
startup — boot only seeds idempotent demo data. Always run migrations first:

```bash
cd backend
.venv/Scripts/python.exe -m alembic upgrade head
```

After changing a model under `app/models/`, generate and apply a migration:

```bash
.venv/Scripts/python.exe -m alembic revision --autogenerate -m "describe the change"
.venv/Scripts/python.exe -m alembic upgrade head
```

Review every autogenerated migration before committing — autogenerate misses some changes (enum
edits, server defaults, the `ltree` extension). The initial migration creates all tables and the
`ltree` extension.

> **Test database is separate.** The suite uses an isolated `gaaex_test` database on the same
> Postgres instance — it is dropped and recreated on each run, so it never touches your dev data.

## 3. Tests

```bash
cd backend
.venv/Scripts/python.exe -m pytest -q
```

Tests run against `gaaex_test` (auto-created from the models, then seeded) using an in-process
ASGI client — no running server needed, but Docker Postgres must be up. Coverage spans auth,
config-driven CRUD, field validation, workflow transitions, access scope, and audit history.

## 4. Architecture in one page

GAAex is built on a small fixed **Kernel Line** of engines; everything a user sees and every
business rule is **configuration interpreted by those engines** — there are no hardcoded screens
or per-entity code paths.

**The kernel engines (fixed):**

1. **WorkItem movement** — lifecycle/state transitions (`app/workflow.py`).
2. **Auth / authz** — identity + permission + org-scope enforcement (`app/access.py`).
3. **Database** — the persistence + config registry.
4. **Audit / log** — an immutable event for every mutation (`Event`).
5. **Security** — sandboxed expression evaluation, default-deny access.

**Config-driven entities** — an entity is defined entirely by rows, never code:

- `EntityDef` — the entity (key, labels, route slug, icon).
- `FieldDef` — its fields (type ∈ text · number · boolean · date · datetime · money · email ·
  phone · select · multiselect · status · ref · ref_user · ref_orgnode · file · formula).
- `StatusDef` — lifecycle statuses (UPPER_SNAKE key + label, one `is_initial`).
- `WorkflowDef` — allowed transitions `{from, to, guard}`.
- `Record` — instances, stored hybrid: core columns + a JSONB `data` bag. One table holds every
  entity type, keyed by `entity_key`.

**Generic CRUD + interpreter** — `routers/records.py` serves `/api/{slug}` for *any* entity by
reading its config and validating against it; the React frontend renders list + form for any
entity from `/meta/entities/{slug}`, with zero per-entity pages. Standing up a brand-new entity
needs only config rows — no code, no restart. That is the core thesis.

**Access model** — `RoleDef` (permissions + scope) + `Assignment` (user → role → org node),
loaded by `app/access.py`. Permissions are `entity.verb` (or `*` / `entity.*`); scope is
`node` | `subtree` | `tenant`, evaluated against the record's org-node `ltree` path. Default-deny.

**Workflow + GXL** — transitions go through `POST /api/{slug}/{id}/transition`, which checks the
transition exists and its guard passes. Guards are **GXL** expressions (`app/gxl.py`) evaluated
in a sandbox (currently `simpleeval`; CEL is the production target). A guard failing or erroring
fails closed.

**Audit** — create / update / delete / transition each emit an `Event` (actor + before/after).
A record's full trail is at `GET /api/{slug}/{id}/history`.

**SuperAdmin Studio** — `POST /meta/entities` lets a super-admin define a new entity (fields,
statuses, transitions) from the browser; it appears in the sidebar and works immediately across
all five kernel engines. The killer test, driven from the UI.

The seeded **CRM module** (Lead, Customer, Contact, Deal + a Ticket) is itself just config — see
`app/seed.py` for how each is assembled via `_make_entity`.

## 5. Conventions

- **Reserved endpoint namespaces:** `/auth/*`, `/meta/*`, `/org-tree`, `/health*`. The generic
  record router owns **`/api/{slug}`** — any new top-level path must avoid `/api/<word>` collisions.
- **Route slugs:** plural-kebab-case (`leads`, `support-tickets`).
- **Entity keys / field keys:** snake_case, singular (`lead`, `owner_node_id`).
- **Status keys:** UPPER_SNAKE (`NEW`, `IN_PROGRESS`) with a human `label`.
- **Permissions:** `entity.verb` (`lead.view`, `customer.create`); `*` and `entity.*` wildcards.
- **Async everywhere** — SQLAlchemy 2.0 async, `async def` routes, `await` the session.
- **Everything written down** — design decisions live in the `../GAAex-Vision/` docs, not only
  in code or chat.
- **Keep the kernel small** — engines stay fixed and generic; new capability is expressed as
  configuration on top, not as new hardcoded paths.
